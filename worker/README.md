# Бот на Cloudflare Workers

Отвечает на `/start` приветствием и кнопкой запуска Mini App.

## Почему не на своей ВМ

Сеть хостинга режет исходящие соединения к `api.telegram.org`: DNS
резолвится (`149.154.166.110`), а connect висит в таймауте. Проверено
с двух адресов Telegram - это блокировка на уровне сети, настройками
контейнера не обходится.

Игру это не затрагивает: Telegram грузит `game.workaem.com` в webview
напрямую, минуя свой API. Через воркер идут только ответы бота.

## Развёртывание

```bash
cd worker
npx wrangler login
npx wrangler secret put BOT_TOKEN         # токен из BotFather
npx wrangler secret put WEBHOOK_SECRET    # тот же, что в .env на ВМ
npx wrangler deploy
```

Wrangler выведет адрес вида `https://workaem-game-bot.<поддомен>.workers.dev`.

## Регистрация вебхука

```bash
curl -sS "https://api.telegram.org/bot$BOT_TOKEN/setWebhook" \
  -d "url=https://workaem-game-bot.<поддомен>.workers.dev/webhook" \
  -d "secret_token=$WEBHOOK_SECRET"
```

Проверить:

```bash
curl -sS "https://api.telegram.org/bot$BOT_TOKEN/getWebhookInfo"
```

В ответе `pending_update_count` должен быть 0, а `last_error_message` - отсутствовать.

## Логи

```bash
npx wrangler tail
```

## Лимиты бесплатного тарифа

100 000 запросов в сутки. Один `/start` - это один запрос, так что
упереться в лимит можно только при очень бурном успехе.

## Таблица рекордов

Хранится в D1 - это SQLite прямо в воркере. Не KV: таблице нужны `ORDER BY`
и `COUNT`, без них нельзя сказать «ты 14-й из 320», а место важнее самого
топа - в первую десятку не попадёт почти никто, а место есть у каждого.

База уже создана, её id прописан в `wrangler.toml`. Если поднимаешь всё
с нуля на другом аккаунте - `npx wrangler d1 create junior-way-board` и
подставить новый `database_id` в тот же блок. Привязка обязана называться
`DB`: под этим именем база видна коду.

```bash
cd worker
npx wrangler d1 execute junior-way-board --remote --file schema.sql
npx wrangler secret put BOARD_SALT
npx wrangler deploy
```

Соль для `BOARD_SALT` удобно взять из `openssl rand -hex 32`.

Проверить:

```bash
curl -sS https://workaem-game-bot.<поддомен>.workers.dev/board | head -c 300
```

Пока база не привязана, воркер отвечает `{"ok":false,"error":"no board"}`,
а игра просто не показывает таблицу. Это осознанное поведение: соревнование
- дополнение к игре, а не условие её работы.

### Что в таблице лежит

Одна таблица `runs` на всё. `mode` различает зачёты: `career` - забег
целиком, `level:7` - седьмой уровень. `bucket` пока всегда `all`; колонка
осталась под недельные срезы, если они когда-нибудь понадобятся - схему
для этого менять не придётся.

Главный зачёт - по уровням: карта каждого уровня у всех одна и та же,
поэтому сравнение честное. Результат уровня приходит на его финише
(`POST /level`), а не в конце забега.

Плюс `totals` со счётчиками для витрины: забеги, растоптанные легаси,
скиллы.

Идентификатор игрока хранится хешем с солью: для таблицы он нужен только
чтобы понять «это тот же человек», а сам id держать незачем. Имя можно
скрыть - в игре есть переключатель, и тогда в топе стоит «Джун #1a2b».

### Кто попадает в таблицу

Только проверяемая личность:

- **Telegram** - подпись `initData` ключом бота. Работает уже сейчас.
- **workaem** - токен, который сайт выдаёт после входа. Ждёт своей
  половины на стороне сайта, см. ниже.

Все остальные - гости: у них не сохраняется ничего, даже локально.
Пускать в общую таблицу неподписанные результаты нельзя: к вечеру первого
дня там будет «Дуров» с миллиардом очков, и таблица обесценится для всех.

Забеги с продолжения (`startLevel > 0`) не идут в общий зачёт - это
проверяется на сервере, а не на клиенте. В таблицы уровней они идут:
уровень считается сам за себя.

### Эндпоинты

```
POST /result   забег целиком: общий зачёт и сообщение в чат
POST /level    результат одного уровня
POST /stats    экран статистики: уровни, общий зачёт, свои места
POST /players  страница списка игроков плюс своё место
GET  /board    короткий топ для стартового экрана
GET  /health   проверка живости
```

## Что нужно сделать на стороне workaem

Одна страница и один общий секрет. Игра уходит на неё, сайт возвращает
подписанный токен, воркер проверяет подпись сам - без обращения к сайту,
чтобы таблица не падала вместе с ним.

```
GET https://www.workaem.com/game/auth?back=<адрес игры>&nonce=<строка>
```

1. Не залогинен - показать обычный вход или регистрацию. Это и есть смысл
   затеи: игра приводит регистрации.
2. После входа вернуть игрока редиректом на
   `<back>#wa=<jwt>&nonce=<та же строка>`.

Токен - JWT с `alg: HS256`, подписанный секретом `WORKAEM_SECRET`
(на стороне воркера задаётся через `wrangler secret put WORKAEM_SECRET`):

```json
{ "sub": "id пользователя", "name": "ник для таблицы", "iat": 1770000000, "exp": 1772592000 }
```

Срок разумно ставить месяц: игру открывают снова и снова. Токен уезжает
во фрагменте, а не в query - фрагмент не попадает ни в логи, ни в Referer.

Пример выдачи на Node:

```js
import { createHmac } from "node:crypto";

const b64 = (o) => Buffer.from(JSON.stringify(o)).toString("base64url");

function issue(user, secret) {
  const now = Math.floor(Date.now() / 1000);
  const head = b64({ alg: "HS256", typ: "JWT" });
  const body = b64({ sub: user.id, name: user.nick, iat: now, exp: now + 30 * 86400 });
  const mac = createHmac("sha256", secret).update(`${head}.${body}`).digest("base64url");
  return `${head}.${body}.${mac}`;
}
```

Страница на сайте есть (`src/app/game/auth/route.ts` в репозитории workaem),
секрет разложен по обеим сторонам, вход включён: `AUTH_READY = true`
в `src/platform/workaem.ts`. Это же и выключатель - отвалится сайт или
секрет, ставим `false`, и игра перестаёт предлагать вход.
